# Хранилище и резервные копии

На Home в разделе «Хранилище и резервные копии» можно запросить постоянное хранилище. Браузер вправе отказать; статус отображается после запроса. Постоянное хранилище уменьшает риск автоматической очистки, но не заменяет внешние копии и не защищает от ручного удаления данных сайта.

При заполнении квоты минимум на 85% Home предлагает скачать копию и очистить старые снимки. Ошибка `QuotaExceededError` при сохранении показывает, что изменения не сохранены; документ остаётся открытым и следующую попытку можно выполнить после освобождения места.

Карточки проектов и снимки показывают UTF-8 размер сериализованного документа. Это размер полезных данных без служебных расходов IndexedDB, превью, состояния редактора и кеша приложения. Для старых записей размер вычисляется при чтении без перезаписи документа. Общая оценка хранилища поступает от браузера и может отличаться.

Очистка предлагает оставить 1, 3 или 5 последних снимков каждого проекта, включая несохранённые документы. Удаление требует подтверждения; как минимум один снимок каждого владельца сохраняется. Обычное автоматическое ограничение по-прежнему оставляет до десяти снимков.

Кнопка скачивания на карточке проекта сохраняет его `.pixprite`. «Резервная копия всех проектов (ZIP)» создаёт архив с файлами `projects/*.pixprite` и `manifest.json`: метаданные проектов, папки и пути файлов. Каждый `.pixprite` можно открыть через обычный импорт; восстановление дерева папок из manifest автоматически пока не выполняется. Имена в архиве защищены от разделителей пути и различаются по ID проекта.

Резервные копии содержат сохранённые версии проектов. Перед экспортом сохраните нужные изменения открытых вкладок; снимки и несохранённые вкладки не входят в этот архив. Скачивание передаёт файл браузеру; приложение не может подтвердить, что пользователь оставил его на диске.

Home напоминает о проекте с несохранёнными во внешнюю копию изменениями, когда с его создания или последней копии прошла неделя. Отдельная копия учитывается только для своего проекта. Напоминание можно отложить на неделю; настройки хранятся локально. Экспорт всех проектов обновляет общую отметку резервной копии.

## Сохранение и восстановление

IndexedDB v8 обновляется без удаления существующих записей. Документ проверяется полным декодированием в Worker до записи. Revision tokens позволяют проверить актуальную предыдущую версию вне write transaction и повторить проверку при конкурентной записи; подробнее — [фоновая обработка](background-work.md). Метаданные проекта, пиксели, состояние редактора и предыдущая исправная версия записываются одной транзакцией. При отмене транзакции остаётся весь предыдущий набор. Первый save также создаёт исходную восстановительную копию; каждый следующий успешный save сохраняет предыдущую валидную версию. Если текущая запись уже повреждена, она не заменит исправную копию. Хранится одна предыдущая версия на проект, отдельно от автоматических snapshots; удаление проекта удаляет и эту копию.

В меню проекта на Home выберите «Восстановить предыдущую версию». Она откроется в новой несохранённой вкладке. Повреждённая запись не удаляется и не перезаписывается; сохраните восстановленную вкладку как новый проект. У старых проектов копия появится при следующем успешном сохранении. Если предыдущая версия отсутствует, проверьте snapshots или внешний `.pixprite` backup.

Рабочая копия с заголовком и состоянием редактора также сохраняется атомарно; overlapping autosaves объединяются: выполняются текущая полезная подготовка и последний запрос после edit burst; устаревший Worker отменяется. Маркеры сохранённой версии и ID нового проекта меняются только после успешной записи. Правки, внесённые во время сохранения, остаются несохранёнными. Ошибки видны в редакторе, повторная попытка сохраняет pending изменения.

Повреждение одной вкладки или старого localStorage-документа не прерывает восстановление остальных. Для рабочей копии с предыдущей исправной версией создаётся отдельная восстановленная вкладка со стабильным ID, чтобы reload не создавал дубликаты. Исходная повреждённая запись и ссылка на неё сохраняются; это не автоматическое исправление оригинала. Успешно мигрированные legacy документы не импортируются повторно, а неудачные записи остаются в localStorage. Защита рассчитана на транзакционные сбои и повреждение отдельных записей; очистка браузером всей базы требует внешней резервной копии.

## Инкрементальные ресурсы

Новые записи `data`, `lastGoodData`, `snapshotData` и рабочие copies в `sessions` содержат лёгкий manifest. Base64 pixels изображений, tilesets и tile references лежат отдельно в `resources` под SHA-256 ключами от вида, размеров и bytes. Запись неизменённого ресурса повторно не выполняется, в том числе между frames, проектами, session copies и snapshots. Совпадения image ID между независимыми файлами не приводят к sharing разных pixels. PNG previews лежат в отдельном `previews`; metadata и preview читаются одним readonly snapshot и обновляются атомарно с соответствующим manifest, когда preview действительно изменился.

Обновление базы создаёт только новые stores. Inline v3/v4/v5/v6 записи читаются без перезаписи и переходят на manifest при следующем save. Все публичные loaders, скачивание проекта, backup ZIP и восстановление возвращают обычный полный `.pixprite`, без внутренних resource pointers. Существующие inline last-good/snapshots сохраняются до обычной замены/очистки.

В write transaction входят новый manifest, отсутствующие resources, metadata/editor, preview и last-good pointers; при abort изменения откатываются вместе. Никакая async Worker работа не ожидается внутри write transaction. После успешных saves одна отложенная idle-задача на burst собирает недостижимые resources; она не задерживает commit/dirty markers, а её ошибка не отменяет уже сохранённый документ. Удаление и cleanup snapshots также запускают сборку: одной транзакцией сканируются project current/last-good, session current/last-good и все snapshots, затем удаляются только ключи без живых владельцев. Для консервативного retention учитываются и declared inventory, и фактические image/tileset/cel pointers: повреждение списка ключей само по себе не удалит существующие pixels. Поэтому удаление проекта не стирает общие pixels открытой рабочей копии или другого snapshot. До отложенной сборки orphan versions могут временно занимать место; тесты и явная очистка могут вызвать `collectUnusedResources` сразу. Ключи ресурсов сверяются при чтении в Worker; отсутствие/подмена одного ресурса не мешает списку и восстановлению других исправных документов.
