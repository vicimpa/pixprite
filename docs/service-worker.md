# Service Worker

Production build создаёт полный offline-снимок приложения. `scripts/vite-service-worker.js` работает после записи Vite output: в `precache-<release>.json` входят окончательный `index.html`, все main/lazy/Worker chunks, CSS, языки, шрифты и public-файлы. `.vite` diagnostics, сам SW и старые precache manifests в список не входят. Release SHA-256 зависит от списка с hashes файлов и исходника SW, поэтому изменение Worker-only chunk, HTML или логики SW создаёт новую версию.

`sw.js` содержит release и integrity manifest. Установка загружает manifest с SHA-256 integrity, затем каждый файл с его integrity; HTTP-ошибка, redirect или несовпадение bytes прерывает установку. Недоустановленный cache удаляется, активная версия остаётся доступной. Список — JSON, поэтому precache не увеличивает JS bundle списком файлов. Файлы скачиваются последовательно, чтобы не держать весь релиз в памяти одновременно.

## Обновление и данные

SW использует cache `pixprite:<registration.scope>:<release>`. Controlled navigation получает HTML своего снимка; запросы ресурсов ищут совпадение только в этом cache. Сервер может уже отдавать новый HTML и удалить старые hashed URLs: открытый controlled клиент продолжит получать старый HTML и все старые chunks из полного снимка. Чужие caches, в том числе со старыми bytes по URL нового релиза, не участвуют в поиске. Не входящие в снимок запросы идут в сеть без runtime caching.

Новый SW проходит установку и ожидает естественной активации. `skipWaiting`, `clients.claim` и принудительной перезагрузки нет. Обновление требует закрыть все вкладки/окна Pixprite этого scope, включая установленную PWA; обычный reload при ещё открытых controlled клиентах сохраняет прежний релиз. Редактор продолжает работать, сохранять и экспортировать несохранённые проекты, пока обновление ждёт. Активация удаляет только предыдущие caches с точным префиксом приложения и scope. CacheStorage других приложений и соседних Pixprite scopes не меняется. Исторический unscoped `pixprite-v1` не удаляется автоматически: его принадлежность конкретному scope доказать нельзя, новый SW его не читает.

SW не открывает и не очищает IndexedDB/localStorage. Рабочие копии, сохранённые проекты, resources, snapshots и состояние сессии восстанавливает обычный механизм редактора. Во время ожидания обновления браузер хранит два полных снимка; нехватка cache storage отклоняет установку нового, не удаляя предыдущий. Очистка данных самим пользователем/браузером остаётся внешней границей сохранности локальных данных.

## Первая установка и offline

Первое HTTP-открытие устанавливает SW, но остаётся uncontrolled. После завершения установки следующее открытие/reload контролируется полным снимком, и встроенные функции, впервые вызываемые offline, получают свои chunks из precache. Это относится и к Worker imports, и к fallback на основном потоке. Precache скачивает файлы, но не исполняет ленивые модули; bundle/network gates по-прежнему проверяют demand execution с заблокированным SW.

До первого controlled открытия согласованность HTML/assets обеспечивает hosting: следует публиковать весь `dist/` как единый релиз и сохранять immutable hashed assets для уже выданного HTTP HTML. SW не может защитить первоначальную сетевую страницу до своего управления. Отсутствие `claim` также не позволяет присоединить HTML предыдущего deploy к новому SW. При оборванном или смешанном deploy integrity отклонит новый offline-снимок; предыдущий установленный релиз продолжит работать. При неудаче самой первой установки offline ещё недоступен, повторная регистрация/проверка обновления может установить исправленный релиз.

Offline-снимок покрывает встроенный редактор, а не удалённые каталоги, ещё не установленные расширения или ресурсы внешних сервисов. Возможности browser APIs, например конкретный WebM encoder, определяются браузером.

## Проверки

`bun test scripts/vite-service-worker.test.ts` проверяет полноту списка, hashes, детерминированность и изменение release при изменении Worker-only файла. `PIXPRITE_E2E_PREBUILT=1 bun run test:e2e e2e/pwa.e2e.ts` проверяет production builds с разными HTML, JS bytes и `assets-a/`/`assets-b/` URLs в изолированных scopes loopback-сервера:

- Первую установку после уже наступившего `window.load`, controlled reopening, полный precache, offline создание/рисование, первое открытие редкого диалога, GIF export/import, reload; отдельно Worker и main-thread fallback.
- Новый deploy с двумя controlled вкладками и двумя несохранёнными документами: отсутствие перезагрузки, старый HTML и недоступные на сервере старые assets, ожидание закрытия всех вкладок, новый HTML с посторонним stale cache, восстановление IndexedDB и совпадение экспортированных pixels.
- Очистку предыдущего релиза с сохранением cache другого приложения и настоящей регистрации Pixprite в соседнем scope.
- Отказ установки из-за отсутствующего файла, неверного HTML, неверного JS или подменённого manifest; удаление частичного cache, доступность прежней версии offline и успешную повторную установку после исправления сервера.

Deployment/fault endpoints существуют только в `e2e/pwa-fixtures.ts`, не попадают в production code и не меняют global deployment других browser tests. Старый editor offline E2E отдельно проверяет reload/рисование/reconnect с реальной root-сборкой.
